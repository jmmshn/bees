# S10 a fresh lead finds the running work

Tests state that lives outside any conversation. Unlike S7, the new lead starts **fresh**: no `--continue` (a new day, `/clear`, a lost session).

1. t0: `build count.txt with the numbers 1 to 500, one per line, in 5 commits of 100 lines each, sleeping 30 seconds between commits (it's a durability test, keep the sleeps)`
2. Poll `git -C <repo> log --all --oneline -- count.txt | wc -l` every 5 s. At **2** commits: log `event: closing lead`, kill the lead's process (pid from `~/.claude/sessions/*.json` with `.name == <lead>`), wait for its pane to return to a shell, then start a **fresh** lead in the same pane with `herdr pane run <pane> "<cmd>"` (intervention):
   - arm a: `claude --name <lead> --append-system-prompt-file <bees>/bakeoff/arms/A-subagents.md`
   - arm b: `claude --name <lead> --append-system-prompt-file <bees>/bakeoff/arms/B-peers.md`
   - arm c: `bs queen`
3. When the new lead is idle → `what's running right now, and how far along is it?` Log what it knows: the worker, its branch, its progress.
4. If it finds the work: wait for ready → `merge it` → merged → `clean up` unless done → `end`. If it doesn't: log `event: work invisible`, say once `there was a count.txt job in progress, find it and finish it`, and continue.

Optimal: the worker keeps going; the fresh lead names the worker and its progress from one status check, without the captain's hint; merge with 5 commits. Captain turns: 3.
