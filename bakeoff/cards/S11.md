# S11 the worker dies mid-job

Tests resuming a long-running worker where it stopped, instead of starting over.

1. t0: `build count.txt with the numbers 1 to 500, one per line, in 5 commits of 100 lines each, sleeping 30 seconds between commits (it's a durability test, keep the sleeps)`
2. Poll `git -C <repo> log --all --oneline -- count.txt | wc -l` every 5 s. At **2** commits, kill the **worker** (intervention) and log `event: worker killed` with the two commit shas:
   - arm b, c: `kill <pid>` of the worker's claude process (`~/.claude/sessions/*.json` whose `.cwd` is the worker's worktree); wait for its pane to return to a shell.
   - arm a: the worker lives inside the lead. Stop it from the lead's background-agent view (`/tasks` or the footer row, select it, `x`). If that isn't possible without asking the lead, log `event: cannot kill a subagent alone` and say to the lead `stop the worker now` instead.
3. Then to the lead: `the worker died at 200 lines. Resume it from where it stopped, don't start over`.
4. Lead reports ready → `merge it` → merged → `clean up` unless done → `end`. Log whether the first two commits (their shas) are still in main's history.

Optimal: the same worker (same branch and worktree, ideally the same conversation) resumes at line 201; the two original commits survive; count.txt is exactly 1..500. Keeper turns: 3.
